1. Alcance

Este documento describe la autenticación y autorización usada por el frontend de RRHH: login local, login con Office 365/Azure AD, recepción de notificación de login por SignalR, gestión de usuarios, roles, menús, permisos de acción, Active Directory local, Azure AD y sesiones activas.

Las evidencias visuales fueron capturadas en modo claro desde el frontend local. Las capturas incluyen una etiqueta de pantalla y, cuando el menú efectivo lo muestra, la opción del sistema resaltada.

2. Arquitectura general

El frontend no autentica directamente contra Microsoft ni contra LDAP. El frontend consume el servicio de autenticación centralizado en RepositoryUta, que expone /api/auth, /notificationHub, /api/azure-management y /api/local-ad. HrBackend valida tokens para los módulos propios de RRHH.

Componente Responsabilidad Fuente revisada
HrFrontend Formulario de login, popup Office 365, WebSocket, almacenamiento de tokens, carga de usuario, menú y permisos. client/src/features/auth/*, client/src/hooks/useNotificationWebSocket.ts
RepositoryUta AuthSystem Emite tokens, valida usuarios locales, genera URL Azure, procesa callback, entrega token por PKCE y administra AD/Azure. Controllers/AuthController.cs, Services/Implementations/AzureAuthService.cs
SignalR Hub Notifica eventos de login Azure al navegador que inició el flujo. Hubs/NotificationHub.cs, Services/Implementations/NotificationService.cs
HrBackend Consume validación centralizada de token y permisos para servicios de RRHH. Infrastructure/Services/TokenValidationService.cs

Flujo resumido

  1. El usuario ingresa al frontend.
  2. El frontend abre conexión SignalR con clientId y browserId.
  3. Para login local, envía correo y contraseña a /api/auth/login.
  4. Para Office 365, solicita URL a /api/auth/azure/url, abre popup Microsoft y espera LoginNotification.
  5. Al recibir tokens, el frontend consulta /api/auth/me, guarda sesión y carga rutas/menús/permisos.
  6. Las llamadas posteriores viajan con Authorization: Bearer <accessToken>.

4. Parametrización previa de clientes en RepositoryUta

Antes de que un frontend externo pueda iniciar sesión con Azure, RepositoryUta debe conocer a esa aplicación cliente. El clientId que envía el frontend a /api/auth/azure/url se valida contra auth.tbl_Applications. Si no existe, está inactivo o eliminado, el backend responde Aplicación cliente no autorizada.

4.5 Checklist de parametrización

  1. Crear fila activa en auth.tbl_Applications.
  2. Confirmar que ClientId sea único, estable y conocido por el frontend.
  3. Generar y guardar ClientSecretHash solo para flujos backend/legacy.
  4. Registrar orígenes CORS del frontend en la configuración de RepositoryUta si aplica.
  5. Crear suscripción activa con EventType = "Login".
  6. Para navegadores, configurar NotificationType = "websocket" o "both".
  7. Verificar que AzureAd:RedirectUri coincida con la URL configurada en Microsoft Entra ID.
  8. Verificar que AzureAd:SecureTokenDelivery = true para entrega con deliveryCode.
  9. Entregar al frontend solo authBaseUrl, notificationHubUrl y clientId.

4.6 Flujo completo que debe implementar cada frontend

  1. Inicializar configuración: authBaseUrl, notificationHubUrl, clientId.
  2. Crear o leer browserId desde almacenamiento local.
  3. Crear conexión SignalR a {notificationHubUrl}?clientId={clientId}&browserId={browserId}.
  4. Registrar handler para LoginNotification.
  5. Ejecutar connection.start().
  6. Invocar JoinApplicationGroup(clientId, null) o JoinApplicationGroup(clientId, "anon").
  7. Invocar JoinBrowserGroup(clientId, browserId).
  8. Generar codeVerifier y codeChallenge.
  9. Solicitar GET /api/auth/azure/url?clientId=...&browserId=...&codeChallenge=....
  10. Abrir la URL devuelta en popup o redirección.
  11. Esperar el evento LoginNotification.
  12. Si llega deliveryCode, llamar POST /api/auth/azure/exchange con deliveryCode y codeVerifier.
  13. Guardar tokens recibidos y consultar GET /api/auth/me.
  14. Construir sesión local y navegar al dashboard del frontend cliente.

4.7 Ejemplo TypeScript para frontend web

import * as signalR from "@microsoft/signalr";

const authBaseUrl = "https://repositoryuta.uta.edu.ec";
const notificationHubUrl = `${authBaseUrl}/notificationHub`;
const clientId = "bienestar-frontend";

function getBrowserId(): string {
  const key = "repositoryuta-browser-id";
  let value = localStorage.getItem(key);
  if (!value) {
    value = crypto.randomUUID();
    localStorage.setItem(key, value);
  }
  return value;
}

function base64Url(bytes: Uint8Array): string {
  let binary = "";
  bytes.forEach((b) => binary += String.fromCharCode(b));
  return btoa(binary).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

function createCodeVerifier(): string {
  const bytes = new Uint8Array(32);
  crypto.getRandomValues(bytes);
  return base64Url(bytes);
}

async function createCodeChallenge(verifier: string): Promise<string> {
  const data = new TextEncoder().encode(verifier);
  const hash = await crypto.subtle.digest("SHA-256", data);
  return base64Url(new Uint8Array(hash));
}

export async function loginWithRepositoryUtaAzure(): Promise<void> {
  const browserId = getBrowserId();
  const codeVerifier = createCodeVerifier();
  const codeChallenge = await createCodeChallenge(codeVerifier);

  const connection = new signalR.HubConnectionBuilder()
    .withUrl(`${notificationHubUrl}?clientId=${encodeURIComponent(clientId)}&browserId=${encodeURIComponent(browserId)}`)
    .withAutomaticReconnect()
    .build();

  connection.on("LoginNotification", async (message: any) => {
    if (message?.eventType !== "Login") return;

    if (!message.deliveryCode) {
      throw new Error("RepositoryUta no envió deliveryCode. Verificar AzureAd:SecureTokenDelivery.");
    }

    const exchangeResponse = await fetch(`${authBaseUrl}/api/auth/azure/exchange`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        deliveryCode: message.deliveryCode,
        codeVerifier
      })
    }).then((r) => r.json());

    if (!exchangeResponse.success) {
      throw new Error(exchangeResponse.message || "No se pudo canjear deliveryCode.");
    }

    const { accessToken, refreshToken } = exchangeResponse.data;
    localStorage.setItem("accessToken", accessToken);
    localStorage.setItem("refreshToken", refreshToken);

    const me = await fetch(`${authBaseUrl}/api/auth/me`, {
      headers: { Authorization: `Bearer ${accessToken}` }
    }).then((r) => r.json());

    localStorage.setItem("userSession", JSON.stringify(me.data));
    window.location.href = "/";
  });

  await connection.start();
  await connection.invoke("JoinApplicationGroup", clientId, null);
  await connection.invoke("JoinBrowserGroup", clientId, browserId);

  const params = new URLSearchParams({
    clientId,
    browserId,
    codeChallenge
  });

  const urlResponse = await fetch(`${authBaseUrl}/api/auth/azure/url?${params.toString()}`)
    .then((r) => r.json());

  if (!urlResponse.success) {
    throw new Error(urlResponse.message || "RepositoryUta no generó URL Azure.");
  }

  const popup = window.open(
    urlResponse.data.url,
    "repositoryuta-azure-login",
    "width=600,height=720,left=200,top=100"
  );

  if (!popup) {
    throw new Error("El navegador bloqueó el popup de Microsoft.");
  }
}

4.9 Ejemplo webhook opcional para backend Node.js

Este ejemplo aplica solo si la suscripción se configura como webhook o both. El navegador seguirá necesitando SignalR si quiere completar el login interactivo en la misma pestaña. 

import express from "express";
import crypto from "node:crypto";

const app = express();
const secret = "secret-hmac-del-webhook";

app.use(express.json({
  verify: (req, _res, buf) => {
    req.rawBody = buf.toString("utf8");
  }
}));

app.post("/api/auth/repositoryuta-webhook", (req, res) => {
  const signature = req.header("X-Webhook-Signature");
  const expected = crypto
    .createHmac("sha256", secret)
    .update(req.rawBody)
    .digest("hex");

  if (signature && signature !== expected) {
    return res.status(401).send("Invalid signature");
  }

  console.log("Evento RepositoryUta:", req.body.eventType, req.body.data?.email);
  res.json({ ok: true });
});

app.listen(3000);

4.10 Errores frecuentes en integraciones

SíntomaCausa probableCorrección
Aplicación cliente no autorizada No existe fila activa en auth.tbl_Applications para el clientId. Crear/activar aplicación y verificar que el frontend envíe exactamente el mismo ClientId.
No llega LoginNotification No existe suscripción Login activa o NotificationType quedó como webhook. Configurar NotificationType = websocket o both.
El evento llega a otro navegador o no llega al actual browserId distinto entre hub y /api/auth/azure/url. Usar el mismo browserId durante todo el flujo.
Código de entrega inválido o expirado deliveryCode expiró, ya fue usado o se perdió el codeVerifier. Reiniciar login Azure. No recargar la pestaña mientras el popup está abierto.
Popup bloqueado El navegador bloqueó ventanas abiertas fuera de una acción del usuario. Abrir popup directamente desde el click del botón de login.
CORS o conexión SignalR rechazada Origen del frontend no permitido en RepositoryUta. Agregar origen en configuración CORS/AllowedOrigins del ambiente.

6. Metodología de login Office 365 / Azure AD

Pasos de usuario

  1. Abrir /login.
  2. Seleccionar la pestaña Office 365.
  3. Presionar Iniciar sesión con Office 365.
  4. El frontend genera un codeVerifier PKCE en memoria y calcula codeChallenge.
  5. El frontend solicita la URL a /api/auth/azure/url enviando clientId, browserId y codeChallenge.
  6. El frontend abre la URL de Microsoft en popup.
  7. Microsoft devuelve el callback al backend.
  8. El backend valida el state, emite tokens y envía una notificación SignalR al navegador que inició el flujo.
  9. El frontend recibe deliveryCode, lo canjea con codeVerifier y completa la sesión.

Servicios consumidos

Método Endpoint Parámetros Uso
GET /api/auth/azure/url clientId, browserId, codeChallenge Genera URL Microsoft y state de OAuth.
GET /api/auth/azure/callback code, state Callback recibido desde Microsoft. Lo consume el backend, no el frontend directamente.
POST /api/auth/azure/exchange deliveryCode, codeVerifier Canje seguro del código de entrega por tokens reales.

Solicitud de URL Azure

GET /api/auth/azure/url?clientId=UTA-Licencias&browserId=browser-uuid&codeChallenge=base64url_sha256

Respuesta de URL Azure

{
  "success": true,
  "data": {
    "url": "https://login.microsoftonline.com/...",
    "state": "base64-state",
    "clientId": "UTA-Licencias",
    "browserId": "browser-uuid"
  }
}

Canje de deliveryCode

POST /api/auth/azure/exchange
{
  "deliveryCode": "codigo-de-un-solo-uso",
  "codeVerifier": "valor-generado-solo-en-la-pestana"
}
Seguridad PKCE: con AzureAd:SecureTokenDelivery=true, el par de tokens real no viaja por WebSocket. El WebSocket entrega solo un deliveryCode de un solo uso, con expiración aproximada de 120 segundos.

7. Recepción de notificación Azure por SignalR

Para que un cliente externo o el propio frontend pueda completar el login Azure, debe conectarse al hub antes o durante el flujo usando el mismo clientId y browserId que envió a /api/auth/azure/url.

Conexión requerida

const hubUrl = "http://localhost:5010/notificationHub";
const connection = new signalR.HubConnectionBuilder()
  .withUrl(`${hubUrl}?clientId=${clientId}&browserId=${browserId}`)
  .withAutomaticReconnect()
  .build();

connection.on("LoginNotification", async (message) => {
  if (message.eventType !== "Login") return;

  if (message.deliveryCode) {
    const tokens = await fetch(`${authBase}/api/auth/azure/exchange`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        deliveryCode: message.deliveryCode,
        codeVerifier
      })
    }).then(r => r.json());

    // Guardar tokens y consultar /api/auth/me
  }
});

await connection.start();
await connection.invoke("JoinApplicationGroup", clientId, "UTA-Licencias");
await connection.invoke("JoinBrowserGroup", clientId, browserId);

Reglas para que el cliente se conecte correctamente

  1. Generar o recuperar browserId antes de pedir la URL Azure.
  2. Conectarse a /notificationHub?clientId=...&browserId=....
  3. Unirse explícitamente a JoinBrowserGroup(clientId, browserId).
  4. Enviar el mismo browserId en /api/auth/azure/url.
  5. Conservar el codeVerifier solo en memoria de la pestaña que inició el login.
  6. Canjear el deliveryCode una sola vez; si expira o falla, reiniciar el flujo Azure.

9. Roles, menú, perfiles y permisos de acción

El sistema maneja dos capas distintas de autorización. La primera decide qué opciones/rutas aparecen en el menú. La segunda decide qué acciones puede ejecutar el usuario dentro de una pantalla.

ConceptoQué controlaServicios
Roles Agrupan acceso y permisos. Ejemplo: Administrador, R_DITIC. /api/roles, /api/user-roles

12. Observaciones técnicas verificadas

Ruta AD local: con la sesión usada para capturas, la pantalla /admin/local-ad carga correctamente, pero /api/auth/me no devolvió un menuItem específico para esa ruta. Por esa razón la captura muestra la pantalla/ruta cargada y no una opción lateral real resaltada. Conviene revisar la fila de menú para /admin/local-ad si se desea acceso visible desde sidebar.
Ruta Azure: la opción visible en el menú aparece como AzureMagnament, manteniendo el mismo texto/ruta del frontend: /admin/AzureMagnament.
