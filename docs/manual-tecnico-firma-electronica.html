3. Interacción entre proyectos

HrFrontend → signature-api

Usa VITE_SIGNATURE_API_BASE_URL. Envía Bearer de RepositoryUta, crea procesos con Idempotency-Key, consulta bandeja/progreso, inicia firma, valida y descarga.

HrFrontend → HrBackend

Sube el PDF original por /api/v1/rh/documents/upload-single. Después calcula SHA-256 en el navegador y registra el fileGuid en signature-api.

signature-api → RepositoryUta

Valida JWT de usuario con JWKS y consulta permisos efectivos por rol. Para llamadas servicio-a-servicio obtiene un token con client credentials de uta-signature.

signature-api → HrBackend

Descarga versiones autorizadas, guarda PDFs firmados en UTA_SIGNATURES y usa /api/v1/rh/email/send-by-guid para invitaciones, recordatorios y documento final.

signature-api → FirmaEC

Envía PDF a POST /servicio/documentos con API key; recibe JWT temporal y genera el URI firmaec://UTA-SIGNATURE/firmar.

FirmaEC → signature-api

Entrega el PDF al callback HTTPS con una API key separada. El API valida sesión, firmante, PDF, certificado y versión antes de persistir una nueva versión.

El API acepta exclusivamente RS256, valida issuer, audience, lifetime y signing key. ConfigurationManager<JsonWebKeySet> refresca JWKS automáticamente cada 5 minutos (refresco mínimo 30 s); ante un fallo de autenticación solicita refresco para tolerar rotación de claves sin reiniciar el contenedor.

4.2 Políticas y permisos

El JWT transporta roles, no la lista completa de permisos. PermissionHandler llama a RepositoryUta: GET /api/role-permissions/effective?roles=…. Se acepta el permiso exacto, ADMIN.ACCESS, o READ_ALL para una lectura propia.

4.3 Token de aplicación

ServiceTokenProvider solicita POST /api/app-auth/token con client ID uta-signature y secreto protegido. RepositoryUta emite un JWT RS256 de aplicación con client_id, token_use=app, roles configurados y vida actual de 60 minutos. El proveedor lo reutiliza hasta dos minutos antes de expirar.

5. Flujos técnicos principales

5.1 Creación

  1. Frontend carga el PDF en HrBackend y obtiene fileGuid.
  2. Calcula SHA-256 del archivo en el navegador.
  3. Envía proceso, firmantes, referencia, flujo e Idempotency-Key.
  4. signature-api valida propiedad/permisos, serializa la numeración y crea proceso, documento, versión 1, participantes, evento, referencia e Outbox.
  5. Outbox envía invitaciones internas/externas sin bloquear la transacción principal.

5.2 Firma automática

  1. Se valida que el participante esté habilitado y que la versión sea actual.
  2. signature-api descarga el PDF desde HrBackend con token de aplicación.
  3. Envía el PDF a FirmaEC; recibe token y arma firmaec:// con URL pública, página y geometría.
  4. FirmaEC mantiene certificado/PIN en el dispositivo y entrega el resultado al callback.
  5. El callback autentica API key, limita tamaño, comprueba PDF/firma/firmante y almacena en HrBackend.
  6. Se crea versión inmutable con PreviousVersionID y SHA-256. Si cambió la versión, responde 409 DOCUMENT_VERSION_CHANGED; nunca fusiona PDFs firmados en paralelo.
  7. Se habilita el siguiente firmante o se completa el proceso; Outbox envía el PDF final.

5.3 Contingencia móvil

Como la app móvil de FirmaEC no siempre notifica el resultado, los endpoints autenticado y público aceptan el PDF entregado por la app. No confían en Content-Type; validan bytes, firma, identidad y versión. El evento queda correlacionado con upload:<participantId>.

Precondiciones

  • Ubuntu x86_64, Docker Engine + Compose plugin, curl, OpenSSL y sha256sum.
  • Host dimensionado (documentado para 8 GiB RAM).
  • api.war y servicio.war en artifacts/.
  • Conectividad institucional hacia SQL Server, RepositoryUta, HrBackend, NAS y HTTPS público.
  • Secretos reales instalados por canal seguro.

Procedimiento base

cd /ruta/UtaElectronicSignatureBackend/docs/docker-containers/firmaec
cp /ruta/FirmaEC/firmadigital-api/target/api.war artifacts/
cp /ruta/FirmaEC/firmadigital-servicio/target/servicio.war artifacts/
chmod +x scripts/*.sh wildfly/entrypoint.sh
./scripts/install-firmaec.sh install

El instalador valida amd64, copia a /opt/uta-containers/electronic-signature, crea directorios, descarga pgJDBC 42.7.13 y verifica SHA-256, genera solo los secretos que pueden ser aleatorios, construye WildFly, levanta PostgreSQL, valida ambos WAR y finalmente inicia signature-api si su imagen ya existe.

Construcción de signature-api

/opt/uta-containers/electronic-signature/scripts/build-signature-api.sh \
  /opt/uta-containers/releases/signature-api-AAAAmmdd-HHMMSS

Su contexto Docker es la raíz completa del repositorio (../../..); no se construye únicamente desde la carpeta del Compose. Usa SDK .NET 9.0.309 para build y runtime 9.0.12, usuario no root, FS read-only y diagnósticos .NET deshabilitados.
